# Reproducibility notes

What has to hold for the published hashes to reproduce, and the traps that cost
real time while assembling this deposit. Read the second half even if the first
half works: several of the traps are silent.

## 1. What the hashes depend on

A published `cnf_sha256` is the hash of a DIMACS file. It is stable under:

* operating system, CPU, filesystem;
* Python minor version (tested on 3.12 and 3.14);
* the order in which instances are generated.

It is **not** stable under a different PySAT version. The cardinality translation
`CardEnc.equals` decides the auxiliary-variable numbering and clause order, so a
different PySAT emits a semantically equivalent instance with different bytes —
and then the deposited proof certificates do not apply to it, because a DRAT/LRAT
proof is tied to a specific clause set.

    python-sat==1.9.dev7      <- a DEVELOPMENT release; this is deliberate
    pypblib==0.0.4
    six==1.17.0

`reproduce.sh` prints a warning if the installed version differs.

### If `python-sat==1.9.dev7` becomes unavailable

The pin is a development release, so PyPI availability is not guaranteed
indefinitely. In order of preference:

1. Install the pinned version from the wheel deposited alongside this artifact (a
   journal deposit should vendor `python_sat-1.9.dev7-*.whl` plus its SHA-256;
   this repository does not, so that the source tree stays text-only).
2. Regenerate with whatever PySAT version is available, and re-run tier 3
   (`make certify`) to obtain fresh certificates for the new bytes. The theorem
   does not depend on the pin — only the byte-level match with the *deposited*
   certificates does. `bin/gen_instances.py --no-hash-check` skips the comparison.
3. Do not "fix" a hash mismatch by editing the manifests. A mismatch is
   information; suppressing it destroys the only link between the source and the
   certificates.

`tests/test_encoder.py` and `bin/encoder_sanity.py` check the encoding's
*meaning*, and they pass under any PySAT version. So a version bump degrades the
deposit from "these exact certificates apply" to "this is the same problem,
re-certify it" — not to "unverifiable".

`make cross-check` is the one thing here that would *survive* the pin
disappearing entirely: `verify/independent_seq_encoder.py` reproduces the
sequential-counter translation from Sinz's paper with no PySAT dependency, and
`bin/cross_check_encoder.py` shows it emits exactly the deposited bytes for all
81 instances. If PySAT 1.9.dev7 becomes unobtainable, that script — not the
library — is what still ties the source to the certificates. `verify/README.md`
is explicit about what this settles and what it does not.

### The file manifest

`MANIFEST.sha256` is a hash per deposited file, checked with

```
shasum -c MANIFEST.sha256
```

and regenerated by `make manifest` (i.e. `bin/make_manifest.sh`) after any edit
to a deposited file. It is bookkeeping about the *download*, not about the proof:
the hashes that carry mathematical weight are the per-instance `cnf_sha256`
fields in `data/*.json`, which `make regenerate` checks. Build products under
`build/` are excluded, so the manifest is stable across runs.

There are two distributions and the manifest differs between them, deliberately.
A git clone carries the **source form** (91 files, no `build/`), which is what
`shasum -c` can check on a tree that has not been built yet. The archival zip
carries the **bundle form** (`bin/make_manifest.sh --with-build`, 176 files),
which additionally covers the 81 pre-generated CNFs and the run records the zip
ships so a referee need not regenerate them. Each is self-consistent; do not
check one distribution against the other's manifest.

### Byte-stable check records

Two of the things a run writes into `build/` are not logs but findings:
`audit.json` (the blocker/orbit audit) and `provenance.json` (the two-encoding
agreement). Both are serialised with `sort_keys=True` and hold no elapsed time,
hostname, or absolute path, so re-running them on a different machine reproduces
the deposited file byte for byte — you can `diff` your copy against ours instead
of reading both. Timings are printed to stdout deliberately, never stored;
`tests/test_manifests.py` fails if a volatile field creeps back in. `reproduce.log`
and `reproduce-summary.tsv` *are* logs of one particular run and will differ.

## 2. Verdict lines: three tools, three wordings, one carriage return

The three tools in the pipeline disagree on how to say "yes":

| Tool | Success line | Exit code |
|---|---|---|
| CaDiCaL 3.0.1 | `s UNSATISFIABLE` | 20 (**not** 0) |
| `drat-trim` | `s VERIFIED` | 0 |
| `cake_lpr` | `s VERIFIED UNSAT` | 0 |

Two traps here, both of which bit the original campaign's own drivers:

* **`drat-trim` writes `\rs VERIFIED`** — the verdict line is preceded by a
  carriage return, left over from its progress display. So `grep -E '^s '` matches
  nothing, silently, and a status file ends up recording no verdict at all while
  the run looks fine. Four of the campaign's five replay drivers had this bug.
  `bin/certify.sh` pipes every verdict through `tr -d '\r'` before matching.
* **Prefix matching accepts the wrong answer.** Matching `^s VERIFIED` would also
  accept a future `s NOT VERIFIED`. `bin/certify.sh` matches the full expected
  line exactly (`grep -m1 -x -F`), one call site per tool.

CaDiCaL's exit code 20 for UNSAT means `set -e` and naive `if solver …` checks
treat success as failure. `bin/certify.sh` checks the verdict line, not just the
exit status.

## 3. Fail closed

`bin/certify.sh` marks a node FAILED and exits non-zero on any of: a missing
verdict line, a CaDiCaL exit code other than 20, a `drat-trim` or `cake_lpr` run
that does not print its exact success line, or an empty LRAT file. It records each
instance's SHA-256 in the node's status file; the comparison against the manifest
is `bin/gen_instances.py`'s job, so run tier 2 before tier 3 — `make certify`
depends on `regenerate` for exactly that reason. This is a correction of the original
campaign, where one replay driver recorded `match=false` for a hash mismatch and
continued to the next node — the mismatch survives in the preserved logs as
`closure-lb-c1042-8-deg3.status: cnf_sha256=a086… expect=NONE match=false`. A
driver that continues past a mismatch produces a log that *looks* like a
verification and is not one.

## 4. Disk

Raw DRAT proofs are large: about 28 GB total across both encodings for the 47
frontier nodes, and the largest single node (`s-r0-2`, sequential) is 2.2 GB raw
and 3.3 GB under `kmtotalizer`. LRAT is larger still — around 14 GB total, with
individual files up to 3.6 GB.

`bin/certify.sh` therefore deletes each node's DRAT and LRAT immediately after
`cake_lpr` accepts it, and refuses to start a node with less than
`C1264_MIN_FREE_GB` (default 60) free. Budget roughly 200 GB of scratch for a full
tier-3 run, or run nodes in batches.

The manifests record `drat_raw_bytes`, `drat_raw_sha256`, `drat_gz_sha256`,
`lrat_bytes` and `lrat_sha256`, so a re-derivation can be compared against the
originals without anyone having to store 28 GB.

## 5. Two DIMACS writers, one output

The campaign wrote DIMACS two ways: a hand-rolled writer and PySAT's
`CNF.to_file`. They were checked to produce byte-identical output (for
`r0-sec-tail`, both give `66f55c22…`), so this artifact keeps only
`encode.write_cnf`, which uses `to_file`. Worth knowing if you compare against
campaign-era scripts and wonder which writer a hash came from: it does not matter.

## 6. The eight non-canonical link witnesses

`data/extensions.json` keys each of the 20 blocked orbits by the SHA-256 of its
canonical (lexicographically least) representative. Twelve of the deposited
witnesses *are* that representative; eight are not, because the campaign solved
whichever labelling its search happened to produce, and the certificate is tied to
those exact bytes.

Rebuilding those eight from the canonical representative gives a different CNF and
therefore a hash mismatch — which is what happened here first, and diagnosing it
took a while. The fix is that the witnesses themselves are deposited in
`data/links/`, `gen_extensions.py` verifies each witness file's own SHA-256 before
using it, and `audit_blocker.py` recomputes each witness's orbit rather than
trusting the manifest's claim.

If you are extending this work: canonicalise the link *before* solving. It costs
nothing and removes the need to deposit witnesses at all.

## 7. Interpreters and paths

The artifact has no absolute paths: `bin/*` derive the repository root from
`__file__`/`$0`, and `PYTHONPATH` is set by the `Makefile`, by `reproduce.sh`, and
by `tests/conftest.py`. To run a script by hand:

```bash
PYTHONPATH=src python3 bin/gen_instances.py --out build/cnf
```

The campaign scripts this artifact was distilled from did the opposite — over
twenty of them `sys.path.insert`ed a worktree path that no longer exists — which
is why none of them are shipped.

## 8. Determinism of the solver runs

Instance *generation* is deterministic. Solver *runs* are not required to be:
CaDiCaL may find a different refutation on different hardware, thread counts, or
versions. That is fine and does not weaken anything — the artifact's claim is that
each instance is UNSAT, witnessed by a checkable proof, and any valid proof
witnesses that. Do not expect `drat_raw_sha256` to reproduce; expect
`cnf_sha256` to reproduce and the new proof to verify.

## 9. Known-good configuration

The deposited hashes were produced on:

* macOS (Darwin 25.5), Apple Silicon
* CPython 3.14.6
* `python-sat` 1.9.dev7, `pypblib` 0.0.4
* CaDiCaL 3.0.1, `drat-trim` (2023 release), `cake_lpr` (CakeML/HOL4 build)

See `docs/TOOLCHAIN.md` for building the three external tools.
